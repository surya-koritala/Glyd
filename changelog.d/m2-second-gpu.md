- On a machine with several GPUs, a model loaded on a GPU other than the first now runs and serves: the engine makes its own GPU current on the thread it works on at every reply and every scheduler round, and a look at any GPU (its free memory, the report after a load, `/v1/glyd/info`) leaves that thread as it was. Before, `serve` of a lossy level (kestrel, swift, wren) on the second GPU of two failed at its first request with "invalid resource handle": the costs object of `/v1/glyd/info` looked at the first GPU after the load, which switched the serving thread to it. Part of #121.
- `/v1/glyd/info`'s `costs.device` now names the GPU the model is served on, not the machine's first.
- `usercheck --ctx plan` loads the model on the GPU its plan names and holds that GPU's memory to the plan. It loaded it on the first GPU and read the first GPU's memory, so on two GPUs a plan of the second read 0 MiB taken and then failed with "invalid resource handle".
