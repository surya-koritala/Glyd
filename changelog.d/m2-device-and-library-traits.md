- The engine reaches the GPU driver through one device-layer interface (`src/device.rs`: NVIDIA's driver, and HIP's runtime in an AMD build, behind the same trait), and Glyd's GPU library and cuBLAS through two more (`src/gpu_ops.rs`), so that another vendor's device layer, or a family of the library's operations moved into the engine's own kernels, is one implementation and not a search of the tree. Nothing changes on the GPU: on an A100 every figure of the bench gate for gemma-4-12B (wren, bf16 and 12-bit KV) is within the noise band of the tree before, and every check gives the same verdicts (`benchmarks/gpu/a100-device-seam-2026-11-24`).
- The engine decides itself which kernel, or the matrix decoded for cuBLAS, takes a packed product of a prompt's length on a GPU, reads the GPU's class from its name, and sizes the 12-bit KV cache's pages, pools and decode workspace, where it asked the GPU library before. `glyd-engine foldcheck` (a development build; in the GPU job) compares each answer with the library's for every GPU class the library knows.
- `glyd-engine/docs/design/kernel-libraries.md`: which operations use NVIDIA's libraries and which Glyd's own kernels, per GPU, with the numbers measured so far and the test that decides each open row; on an A100 cuBLAS multiplies a decoded matrix 2-10% faster than Glyd's own dense product, and keeps it.
- The engine unpacks the packed layouts to bf16 and makes the experts' routing plan with its own kernels, compiled from the GPU library's own source into the engine (`gpu/glyd_gpu_kernels.h`, `glyd-engine/kernels/fold.cu`), not by calling the GPU library; `glyd-engine foldcheck` compares every output with the library's. A development build's `GLYD_ENGINE_FOLD=lib` runs the library's instead.
