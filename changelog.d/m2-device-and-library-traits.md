- The engine reaches the GPU driver through one device-layer interface (`src/device.rs`: NVIDIA's driver, and HIP's runtime in an AMD build, behind the same trait), and Glyd's GPU library and cuBLAS through two more (`src/gpu_ops.rs`), so that another vendor's device layer, or a family of the library's operations moved into the engine's own kernels, is one implementation and not a search of the tree. Nothing is meant to change on the GPU; speed before and after: not measured yet.
- The engine decides itself which kernel, or the matrix decoded for cuBLAS, takes a packed product of a prompt's length on a GPU, reads the GPU's class from its name, and sizes the 12-bit KV cache's pages, pools and decode workspace, where it asked the GPU library before. `glyd-engine foldcheck` (a development build; in the GPU job) compares each answer with the library's for every GPU class the library knows.
- `glyd-engine/docs/design/kernel-libraries.md`: which operations use NVIDIA's libraries and which Glyd's own kernels, per GPU, with the numbers measured so far and the test that decides each open row.
