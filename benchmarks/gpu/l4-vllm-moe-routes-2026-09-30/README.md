# A mixture of experts' two ways to run, by tokens a step, in vLLM on an L4 (2026-09-30)

granite-3.1-3b-a800m-instruct under `--quantization glyd`, in the smallest layout (`mma`), the L4's layout. Each MoE
layer holds 40 experts, routes each token to 8, and has hidden 1,536 and intermediate 512. The plugin has two ways to
run a layer's experts, picked by tokens a step with `GLYD_MOE_DECODE_MIN` (`-1`: always the first, `1`: always the
second; by default the second from 1,152 tokens a step, as exact mode runs it).

This directory measures both, per layer and per step, and serves with the default.

## Per layer (`moe_routes.py`: `routes-*.json`)

The model's first MoE layer, T random tokens each routed to 8 experts at random, the GPU time of a call (the median of
20, after a warm-up). bf16's is vLLM's own kernel on the bf16 experts, from a bf16 run.

| 8 | 0.578 | 1.813 | 3.14x | 0.850 |
| 64 | 0.843 | 2.272 | 2.70x | 1.020 |
| 256 | 1.204 | 2.397 | 1.99x | 1.141 |
| 512 | 1.421 | 2.520 | 1.77x | 1.217 |
| 768 | 2.043 | 2.692 | 1.32x | 1.315 |
| 1,024 | 2.755 | 2.844 | 1.03x | 1.444 |
| 1,152 | 2.991 | 2.890 | 0.97x | 1.511 |
| 1,280 | 3.324 | 3.049 | 0.92x | 1.656 |

- **Setting 1 is the faster from 1,152 tokens a step**, the default's switch.
- **Setting -1 against bf16's layer:**
  - to 128 tokens a step, it takes less time than bf16's layer;
  - from 256, more (1.06x at 256, 2.0x at 8,192).
  - Setting 1 never beats bf16's layer.
- **The two settings' outputs** differ by at most 6.9e-3 (relative), as any two summation orders do.

"Setting -1" and "setting 1" run one way throughout (`GLYD_MOE_DECODE_MIN=-1` and `=1`); "default" is the plugin's
default, the second way from 1,152 tokens.

The default takes each step's faster way. A prompt of 2,048 tokens takes 8% less GPU time than setting -1 throughout,

than bf16's (47.2 against 38.3 ms at 256).

## Serving (`bench-routed/`: the default, `bench-grouped/`: setting -1)

`vllm bench serve`, warm with the cold start noted, `--gpu-memory-utilization 0.9`, 1,024 tokens in and 256 out. There
were 64 prompts at 1 request a second, 128 at 4 and 256 at once, and each mode had one run.

| Rate (req/s) | bf16 | Glyd, default | Glyd, setting -1 throughout |
| :--- | :--- | :--- | :--- |
| 1 | 0.92 req/s; TTFT 105 ms; TPOT 19.4 ms | 0.94; 134; 16.1 | 0.93; 134; 16.1 |
| 4 | 3.13; 155; 46.2 | 3.04; 236; 52.0 | 3.06; 206; 50.9 |
| inf | 5.10; 9,365; 106.7 | 4.38; 9,229; 140.6 | 4.27; 9,383; 145.4 |

- **KV cache:** bf16 211,968 tokens, Glyd default 237,648 (1.12x), setting -1 throughout 240,352. The default's extra
  scratch costs 1.1% of Glyd's KV cache here.
- **Default against setting -1 throughout:**
  - 1.03x the requests a second saturated, each token 3% sooner;
  - the same at 1 request a second;
  - at 4 a second, the first token later (236 against 206 ms, one run each).
- **Glyd against bf16 at saturation:** 0.86x the requests a second, each token 32% later. This is the generation steps'
  cost from 64 sequences, which the setting does not change.

## Files

- `m8_moe.sh`: the per-layer runs and the per-step profiles.
  - `m8_moe.log` is its first try, whose profiles stopped on a token id outside granite's vocabulary; the fix is
    `profile_steps.py` drawing ids from the model's vocabulary. `m8_moe2.log` is the second try.
  - The finer per-layer runs (`routes-*-fine.*`) were run by hand, with the same script and `TOKENS` set.
- `m8_route.sh`: `test_vllm.py`, the profile and the two benches.
- `routes-*.json`, `steps-*.json`, `bench-*`: the results; `summary.txt` in each bench regenerated by
  `bench_summary.py`.
