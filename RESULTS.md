## Blocked gates

No threshold in GOAL.md has been altered. This section records what was tried
and measured, so the remaining gates can be attacked with evidence rather than
guesses.

### G3 and G5: decompression speed

Decompression went from 0.488x to 0.68x of reference liblz4 this session. The
gate needs 1.05x. Every change below was measured on Silesia with all other
code identical.

Kept, in order of effect:

| Change | Decomp | vs liblz4 |
|---|---:|---:|
| baseline | 2.694 GB/s | 0.488x |
| unconditional literal wildcopy | 4.053 | 0.733x |
| raw-block bypass at 4% savings | 4.209 | 0.759x |
| remove AVX-512 decoder | 4.380 | 0.794x |
| format v3 (smaller streams, more branches) | 3.733 | 0.677x |
| 256 KB blocks | 3.744 | 0.681x |

Rejected, each reverted:

| Change | Effect |
|---|---|
| indexed do-while match copy instead of pointer increments | -18% |
| consolidate 7-way offset dispatch to 3 cases with pshufb | -15% |
| 16-byte literal stores instead of 32-byte | no change |
| pointer cursors for token/offset/extras streams | no change |
| skip the literal store when lit_len == 0 | -41% |

Two lessons hold consistently. The compiler generates better code from
incrementing pointers than from base-plus-index addressing. And an
unpredictable branch costs far more than a wasted vector store: guarding the
literal copy on `lit_len != 0` lost 41% even though roughly 40% of v3 tokens
carry no literals.

The remaining gap is per-token overhead, and decode speed tracks token density
directly. Closing it needs fewer tokens or a genuinely branchless multi-token
decode, not further micro-optimisation of the current loop.

### G4: compression speed

0.49x of liblz4, gate needs 1.00x. Least explored of the failing gates.

The hash-table sweep is the core evidence. Ratio and compression speed trade
off against each other almost exactly, and the two ends of the sweep are the
best ratio and the best speed:

| Table | Ratio vs liblz4 | Comp vs liblz4 |
|---|---:|---:|
| 16 KB | 0.867x | 0.626x |
| 32 KB | 0.885x | 0.584x |
| 64 KB | 0.895x | 0.532x |
| 128 KB | 0.901x | 0.505x |
| 256 KB | 0.905x | 0.504x |

Also rejected: capping the lazy-match probe at one byte past the incumbent
match, which produces byte-identical output but ran 12% slower, because the
probe almost always fails inside the first 32-byte vector anyway and the extra
bound computation costs more than the comparison it saves.

Lazy matching cannot simply be removed: it is worth about 5% ratio, and G2
currently passes at 1.045x with only 0.025x of headroom.

### G6: workload ratios, and a conflict between gates

The Source Code workload is the blocker. liblz4 reaches 246.8x where Alatirok
reaches 74.2x, after block decoupling doubled it from 36.8x.

The cause is output segmentation, not match quality. Both codecs use a 64 KB
match window. liblz4 compresses the whole 25 MB buffer as a single block, so a
match length is an unbounded varint and one match can span megabytes. Alatirok
emits independent blocks and a match cannot cross a block boundary, so raising
the block size from 64 KB to 256 KB exactly doubled the ratio.

This puts G6 in direct tension with G7. G6 rewards one enormous block; G7
rewards many small independent blocks that decode in parallel and requires
16-core decompression at or above 10 GB/s. Satisfying both needs a format where
blocks remain independently decodable while matches may still reference and
extend across them, which the current header design cannot express.

### Build flags materially change the numbers

Static disassembly of `decompress_avx2` in the shipped build shows the literal
wildcopy compiled to `vmovdqu64 %zmm0`, a 512-bit AVX-512 instruction. The
explicit AVX-512 decoder was removed earlier for measuring slower, but with
`-C target-cpu=native` LLVM re-introduces 512-bit codegen by auto-vectorising
the 32-byte loop.

Disabling AVX-512 codegen entirely removes every `zmm` from the decoder,
leaving 18 `ymm`. Measured like-for-like from the same clone and corpus:

| Build | Comp vs liblz4 | Decomp vs liblz4 |
|---|---:|---:|
| `-C target-cpu=native` (zmm present) | 0.482x | 0.678x |
| AVX-512 codegen disabled (ymm only) | 0.509x | 0.630x |

512-bit registers help the decoder and hurt the compressor, by 7% and 6%.
Neither configuration passes G3 or G4, so no verdict changes, but two
consequences are worth recording.

GOAL.md Section 1 specifies `RUSTFLAGS="-C target-cpu=native"` while
`.github/workflows/ci.yml` builds with `x86-64-v3`, which has no AVX-512. CI
therefore measures the second row. A gate evaluated in CI would differ from a
local run by 6-7% on both speed axes.

And the earlier AVX-512 removal result was narrower than it appeared.
Hand-written 64-byte copies throughout the decoder lost on all 12 files, but
compiler-chosen 512-bit stores in the literal path specifically are a win.
Vector width is not uniformly good or bad; it depends on which copy it is
applied to.

### Notes on the procedure

Every earlier figure in this repository was taken with `--fast`, a single short
run. This section's numbers come from the Section 1 procedure instead: a fresh
clone built in a clean Linux directory, corpus re-downloaded including the
enwik8 holdout, median of five measurements each at least one second, single
core pinned internally.

Strict measurement does not change any verdict. Silesia decompression reads
0.66x of liblz4 against 0.68x in fast mode, compression 0.48x against 0.48x,
ratio 1.04x against 1.04x. liblz4 itself measures slightly faster under strict
timing (5.69 GB/s against 5.51), which widens rather than narrows the gap.

The failing gates fail by large margins, not marginal ones: G3 needs 1.05x and
reads 0.66x, G4 needs 1.00x and reads 0.48x. No plausible measurement error
accounts for a gap of that size.
