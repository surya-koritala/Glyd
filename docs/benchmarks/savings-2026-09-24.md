# The savings calculator's ratios, 2026-09-24

The rows behind [docs/savings.html](../savings.html), measured on the
Ryzen box (AMD Ryzen 9 7950X3D, 16 cores, 32 threads, Ubuntu) with
`scripts/calc_rows.sh` against zstd 1.5.7, LZ4 1.10.0 and gzip 1.14,
Glyd at v0.14.9. Every Glyd output was decoded and compared with its
input; none differed. Raw rows in `benchmarks/calc/rows.tsv`, the
machine and the exact script in `benchmarks/calc/machine.txt`. The
bucket row is the store's terabyte gate
([report](store-gate-2026-09-24.md), v0.14.8).

Record mode reads cost 3–5× zstd's CPU on logs, SQL and CSV. Parquet
reads cost 15–50× (every page is re-encoded, byte for byte, by Glyd's
own port of the writer's zstd or snappy). Where data is read many
times, that CPU can outweigh the bytes saved.

Against the first pass of this measurement (v0.14.8's code, the same
machine), v0.14.9's decoder no longer spins while it waits for the
units ahead of it: decompress CPU at the plain levels fell by up to
65% (logs `--max` 3.08 → 1.09 s, SQL 3.83 → 2.68 s). Units no longer
follow the thread count: this 32-thread machine used to cut an input
twice as finely as the 16-vCPU gate instance. JSON at `--ultra` came
out 5.4% smaller (it was within 1% of zstd -19; now 5% under it); the
other rows moved under 1%.

Where Glyd is behind: `--max` against zstd -19 on logs, JSON and
versions (`--max` is the fast tier and runs without the 128 MB
matcher since v0.14.4; zstd -19 writes at 2–10 MB/s); `--ultra`
without `-r` on the telemetry CSVs (8.38× against 8.63×) and JSON
lines (29.81× against 30.07×).
