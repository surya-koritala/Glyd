# Benchmark suite, 2026-09-19: Glyd against zstd and LZ4 on 8.7 GB of real data

The program in [README.md](README.md), run on AWS by
`scripts/bench_aws_suite.sh` at commit `3a0654bb` (v0.4.0 candidate):
one c7g.2xlarge (Graviton3, Neoverse V1, 8 vCPU, 1 MB L2 per core) and
one c7i.2xlarge (Sapphire Rapids, Xeon Platinum 8488C, 8 vCPU), Ubuntu
24.04, rustc 1.98, libzstd 1.5.7 (in-process) and the zstd 1.5.5 / lz4
1.9.4 CLIs. Raw results: [`benchmarks/suite/`](../../benchmarks/suite/).
Every table below is generated from them by `scripts/report_suite.py`.

## What was verified first

- `scripts/verify_roundtrip.sh` on both machines: NASA log, a GitHub
  Archive hour and a Parquet file at every level, single- and
  multi-core, through the CLI: 30 round trips byte-exact, 240
  corrupted copies rejected or decoded exactly. The same on the whole
  8.7 GB corpus on the development machine: 180 round trips, 0
  failures.
- Every decode in the tables was compared with its input before its
  time was recorded; the S3 workflow sha256-checked every file.

## What this says

- **Storage**: `--max` stores less than zstd -3 on JSON and logs (3-9%)
  and ties on SQL dumps and Parquet; `--ultra` stores 1.5% more than
  zstd -19 everywhere. The default level stores 4% less than LZ4.
- **Reads**: with several cores Glyd decodes 3-7x faster than zstd
  because its output decodes in parallel; on one core `--max` is 9%
  faster than zstd -3 on Graviton3 and 22% slower on Sapphire Rapids
  (the x86 decoder gap, known from Silesia, is wider on this data).
- **Writes**: Glyd `--max` compresses at 0.65-0.78x zstd -3's speed.
  Profiled on Graviton3: the level's match finder uses 2 MB of tables
  against the core's 1 MB L2 and misses cache 0.44 times per byte;
  zstd -3's tables are 768 KB. Smaller tables cost 3.5% of ratio on SQL
  dumps for 27% of speed (measured); the ratio was kept.
- **Small objects**: zstd is 1-3% denser at 1 KB, ties at 4 KB, and is
  1.7-2x faster to compress and 1.4-1.7x faster to decompress per
  object on the server cores (the gap is smaller on Apple silicon).
- **Cost**: on a terabyte stored for a year and read once a month,
  `--max` and zstd -3 are within 1% of each other whichever way the
  instance is billed (CPU seconds above; wall time of a dedicated
  instance in the second table of each S3 section, where Glyd's
  parallel paths make it the cheaper by 1%). Read ten or a hundred
  times a month and billed by CPU, zstd -3 is cheaper because the Glyd
  CLI spends more CPU per read (its parallel decode, a checksum per
  block, and a whole-file buffer against zstd's streaming; 13.7 vs
  10.6 CPU seconds per 8.7 GB on Graviton3, 20.9 vs 10.3 on Sapphire
  Rapids); billed by wall time the reads cost the same (both bound by
  the volume). `--ultra` against zstd -19: 2% cheaper at one read a
  month by CPU, 12% dearer at a hundred; 0.3-3.5% cheaper by wall
  time.

## What has to change for Glyd to be the cheaper choice

1. The `--max` finder's cache footprint (writes at 0.65-0.78x zstd -3).
2. The CLI's decode path: stream unit by unit instead of holding the
   whole file, make the checksum optional as zstd does, and stop the
   parallel decode from spending more CPU than the sequential one.
3. Small objects: a single-pass decoder for compact blocks and a
   cheaper per-object encoder.
4. The x86-64 decoder (0.77x zstd -3 on one Sapphire Rapids core).

## Method notes

- Large files: whole-file compress and decompress in memory; median
  of three repeats (two for `--ultra` and zstd -19 at 8 threads; the
  single-thread pass ran the fast codecs only, `--ultra` and zstd -19
  taking an hour each over 9 GB). Peak memory is a child process on the
  file's first 64 MB: input, compressed and decompressed buffers
  included.
- zstd: the one-shot API for single-thread compression and every
  decompression, the streaming encoder with zstdmt at 8 threads.
  LZ4: liblz4's frame format, level 1, one thread. Small objects: LZ4
  is lz4_flex's block API with an external dictionary (liblz4's Rust
  binding exposes none), given zstd's trained content.
- Compressed bytes include each codec's own framing; Glyd writes a
  4-byte checksum per block, zstd's frames carry none by default.
- The S3 workflow ran the real CLIs (`glyd --max -m`, `zstd -3 -T0`,
  `lz4 -1`, ...) over the 18 files, uploaded and downloaded them with
  the AWS CLI in the same region, and verified every file. Compress and
  decompress wall times there are bound by the instance's EBS volume
  (500 MB/s) for every codec; the cost model uses CPU seconds.
- A first run was discarded: its harness allocated a fresh output
  buffer for Glyd on every repeat and had zstd on its streaming API,
  which showed zstd decoding 40% faster than Glyd on logs; corrected,
  the same file decodes 1,742 (Glyd `--max`) against 1,645 MB/s (zstd
  -3) on Graviton3.
