# Benchmark suite, 2026-09-21: Glyd v0.9.2 against zstd and LZ4 on 8.7 GB of real data

The program in [README.md](README.md), run on AWS by
`scripts/bench_aws_suite.sh` at commit `95041e7` (the max level's
finder tables at zstd -3's size): one c7g.2xlarge (Graviton3, Neoverse
V1, 8 vCPU, 1 MB L2 per core) and one c7i.2xlarge (Sapphire Rapids,
Xeon Platinum 8488C, 8 vCPU), Ubuntu 24.04, rustc 1.98, libzstd 1.5.7
(in-process) and the zstd 1.5.5 / lz4 1.9.4 CLIs. Raw results:
[`benchmarks/suite/`](../../benchmarks/suite/). Every table below is
generated from them by `scripts/report_suite.py`. The previous report
is [suite-2026-09-20.md](suite-2026-09-20.md); what changed since it
is the finder's table size (2 MB to 768 KB), measured first on one
core of each machine ([`benchmarks/max/`](../../benchmarks/max/)).

## What was verified first

- `scripts/verify_roundtrip.sh` on both machines: NASA log, a GitHub
  Archive hour and a Parquet file at every level and mode, single- and
  multi-core, through the CLI: 42 round trips byte-exact, corrupted
  copies rejected or decoded exactly.
- Every decode in the tables was compared with its input before its
  time was recorded; the S3 workflow sha256-checked every file.

against 10.7 s over the corpus in the S3 workflow), so `--max` is the
cheapest row at every read rate there.
