The program in [README.md](README.md), run on AWS by
`scripts/bench_aws_suite.sh` at commit `00f7151` (the v0.4.0 code with
record mode and the long-distance matcher; the S3 workflow section was

## What this says

- **Storage**: `--max` now stores 2.8% less than zstd -3 over the
  corpus and 22% less on JSON events (the 128 MB matcher; 9% before);
  `--ultra` equals zstd -19 (0.1%) and is 9.8% smaller on JSON. Record
  mode is the large lever: `--max -r` stores 19% less than zstd -3 and
  2% less than zstd -19 while compressing at 540-675 MB/s on 8 cores
  against zstd -19's 10-13; `--ultra -r` stores 10% less than zstd -19
  (SQL dumps 30%, logs 9%). Parquet stays where it is.
- **Reads**: with 8 cores Glyd `--max` decodes 3-6x faster than zstd
  -3 and record mode 1.6-2.7x; on one core `--max` is 3% faster than
  zstd -3 on Graviton3 and 20% slower on Sapphire Rapids (the x86
  decoder gap, unchanged).
- **Writes**: `--max` compresses at 0.58-0.66x zstd -3's speed on one
  core (0.65-0.78x before the matcher, whose pass is gated but still
  costs on text, logs and JSON), 0.61-0.64x at 8 threads. Record mode
  halves that again: its transform runs at 200-400 MB/s per core. This
  is the cost of the storage above.
- **Cost**: at one read a month `--max` and zstd -3 are within 2% of
  each other either way the instance is billed; at ten or a hundred
  reads a month and billed by CPU, zstd -3 is cheaper because the Glyd
  CLI spends more CPU per read (14.4 vs 10.7 CPU seconds per 8.7 GB on
  Graviton3, 20.8 vs 10.3 on Sapphire Rapids: the parallel decode, a
  checksum per block, a whole-file buffer). Record mode stores 19%
  less than zstd -3 and is the cheapest choice at one read a month
  (16% under zstd -3 by CPU, 18% by wall time) and at ten reads by
  wall time; its reads spend 2.2-3x zstd -3's CPU (the rebuild of the
  columns), so at a hundred CPU-billed reads a month zstd -3 wins.

## What has to change for Glyd to be the cheaper choice at every read rate

1. The CLI's decode path: stream unit by unit instead of holding the
   whole file, make the checksum optional as zstd does, and stop the
   parallel decode from spending more CPU than the sequential one.
2. The `--max` finder's cache footprint and the matcher's pass (writes
   at 0.58-0.66x zstd -3).
3. Small objects: a single-pass decoder for compact blocks and a
   cheaper per-object encoder.
4. The x86-64 decoder (0.80x zstd -3 on one Sapphire Rapids core).

## Method notes

- Large files: whole-file compress and decompress in memory; median
  of three repeats (two for `--ultra`, `--ultra -r` and zstd -19 at 8
  threads; the single-thread pass ran the fast codecs only). Peak
  memory is a child process on the file's first 64 MB: input,
  compressed and decompressed buffers included (record mode's units
  and column streams put it at 0.9-1 GB).
- zstd: the one-shot API for single-thread compression and every
  decompression, the streaming encoder with zstdmt at 8 threads.
  LZ4: liblz4's frame format, level 1, one thread. Small objects: LZ4
  is lz4_flex's block API with an external dictionary (liblz4's Rust
  binding exposes none), given zstd's trained content.
- Compressed bytes include each codec's own framing; Glyd writes a
  4-byte checksum per block, zstd's frames carry none by default.
- The S3 workflow ran the real CLIs (`glyd --max -m`, `glyd --max -r
  -m`, `zstd -3 -T0`, `lz4 -1`, ...) over the 18 files, uploaded and
  downloaded them with the AWS CLI in the same region, and verified
  every file. Compress and decompress wall times there are bound by
  the instance's EBS volume (500 MB/s) for every codec; the cost model
  uses CPU seconds.
