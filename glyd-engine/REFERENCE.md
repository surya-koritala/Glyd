# glyd-engine reference

Paths beginning `src/`, `kernels/`, `tools/`, `jobs/`, `data/` and `tests/` are glyd-engine's; any other path is from the repository's root.

Glyd's own inference engine, in Rust. It runs the families of `src/support.rs`: the plain dense kind (Llama-style pre-norm decoders), the Qwen3.5 layout (Qwen3.5, 3.6 and 3.8, dense and with experts), Qwen3.8-Flash-Next, Gemma 4, Nemotron-H, Kimi-K3, GLM-5.3-Flash, DeepSeek-V4 and Muse Spark. A family is a description of layer kinds (`src/runtime/describe.rs`) lowered to the executor's operations (`src/dynamic/lower.rs`) and run by one executor (`src/dynamic/`) through one scheduler (`src/sched.rs`); the executor's one loader (`Dyn::new_placed`) reads the weights from the description, so a family adds a description and no engine, loader or server of its own. The machine is an NVIDIA GPU of the Ampere generation or newer (an AMD RDNA 3 or 4 in a development build with `GLYD_HIP=1`).

A matrix is held in one of three forms (`Mat` in `src/kern35.rs`): packed in Glyd's layouts (the tiered and 12-bit lossless layouts at penguin, the block layouts at the lossy levels), bf16 as the checkpoint has it where the library does not pack it, or FP8 as released with its block scales (`src/f8.rs`: the E4M3 bytes bit for bit, GLM-5.3's release). The KV cache is bf16 pages, or the 12-bit lossless pages where the plan takes them: `GLYD_KV=lossless` asks for them (Gemma 4 with `--no-draft`; the plain dense kind under `serve`) and the plan takes them only where they reserve no more than bf16 (the plan paragraph below), their tables made on the first run and kept (`kv12/` of the cache). Decode steps are CUDA graphs. The terminal chat, the chat page and the OpenAI, Anthropic and Ollama APIs (`docs/serve-api.md`) are one scheduler's requests.

The engine's GPU kernels are its own (`kernels/*.cu`, in the program's fatbin: CUDA 13's, and in a release CUDA 12's as well, which the driver's version picks): a CUDA build loads no GPU library. It opens the CUDA driver at run time, and cuBLAS (`libcublas.so.13` or `.12`) where the machine has it, for long prompts; the machine needs the driver and nothing else. `GLYD_GPU_LIB=PATH` names Glyd's GPU library (`libglyd_gpu_cuda13.so`, C API 26: its functions are found by their names) for the checks that compare with it (`foldcheck`, `packcheck --gpu`, `glyd-gpu verify`); with it unset (or `none`) a CUDA build loads none. An AMD build loads `libglyd_gpu_hip`, beside the program or on the loader's path. The engine ships in the release's tarballs (`glyd` with the engine linked and `glyd-engine` a link to it; Linux x86_64 and aarch64, and a Windows x86_64 zip) and in the `glyd-gpu` wheels (Linux x86_64 and aarch64), where `glyd run` starts it.

## Commands

The commands of a release build are the table in the root crate's `src/cmdtable.rs` (`glyd help COMMAND`, `docs/glyd.1`) and `glyd-engine/src/entry.rs`: `run`, `serve`, `connect`, `doctor`, `login`, `supports`, `preflight`, `fetch`, `prepare`, `pull`, `ls`, `rm`, `names`, `service`, `ps`, `stop`, `bench`, `quality`, `verify`, `costs`, `rates`, `fit`, `rangeworker`, and `--version`, with `qwenserve`, `qwenget`, `qwenbench` and `qwenmcp` for Qwen3.8-Flash-Next's packs of codebook experts.

    glyd run Qwen/Qwen3.8-27B                 # the glyd program asks glyd-engine first (`glyd-engine preflight MODEL`) and runs it as its child where it says it will certainly run the model here, else vLLM; one line says which
    glyd-engine run MODEL[:LEVEL]             # the first run downloads the model and packs it for this GPU; then a chat here and at http://127.0.0.1:8000
    glyd-engine run MODEL --prompt "Say hello" --no-think                # one answer on stdout (the thinking on stderr); `-p` is `--prompt`; a prompt on stdin works too
    glyd-engine serve MODEL --port 8000 [--api-key KEY]                  # the APIs of docs/serve-api.md, the chat page at /, the scheduler's counts at /stats
    glyd-engine fit MODEL[:LEVEL] [--machine NAME|FILE]                  # what a run would do on this computer, or a described one: level, placement, context, predicted tokens a second
    glyd-engine doctor                         # what this computer has for running models, each check with the line that fixes it
    glyd-engine login                          # a Hugging Face token (for gated models), saved where `hf login` keeps it
    glyd-engine supports MODEL                 # exit 0 if the engine runs MODEL's kind of model, 3 if not (no GPU is looked at)
    glyd-engine preflight [MODEL]              # before anything is downloaded: exit 0 if the engine will certainly run MODEL on this computer, 3 (the reason on stderr) if not, 1 if that could not be told; with no MODEL, the GPU alone
    glyd-engine fetch MODEL | prepare MODEL    # the model downloaded (no GPU) | downloaded and packed for this GPU

`MODEL` is a short name (`gemma4:12b`), a Hub name (ORG/NAME), a directory in the Hugging Face cache layout or one `pack` made, or a GGUF file; `MODEL:LEVEL` is penguin (lossless, the default), kestrel, swift, wren or hummingbird, and `--lossy` is `:kestrel` (`src/levels.rs`). The flags `run` and `serve` take: `--context N` (`--ctx`; a context that does not fit is shortened as `fit` says, down the degrade ladder below), `--users N` (1 to 64, default 4: the replies decoded together, as many as the GPU's memory holds; a model with a draft model, split across GPUs, or with an operation that takes one sequence runs one at a time), `--layout` (`auto`, `mma`, `mma12` at penguin; the lossy levels' own are in `src/args.rs`), `--temp T`, `--host`, `--port` (`--host` other than this computer's needs a key or `--insecure-no-auth`), `--yes`, `--with MODEL2` (`serve`), `--expert-cache GIB` (the GPU memory for the places of the expert cache), `--host-memory GIB|auto` (the computer's memory a mixture of experts' experts may take) and `--cpu-threads N` (the threads that compute the experts that are not on the GPU). `glyd run` and `glyd serve` give the engine the flags they were given and no others. Models and their packs are kept in the Hub cache (`HF_HOME`, `HF_HUB_CACHE`) and in `$GLYD_CACHE` (default `$XDG_CACHE_HOME/glyd`, else `~/.cache/glyd`: `packed/<model>-<revision>-<layout>/`, `kv12/`, `plans/`).

**Which runner, and which GPU.** Where the Python tool is installed, `glyd run` and `glyd serve` are its: it asks the engine's `preflight` first, and starts the engine as its child where it says yes, else runs vLLM with one line saying why (`glyd-gpu-py/glyd_gpu/engine.py`); where there is no tool, the engine (linked, or beside the program) runs the command and its refusals are the last word. A plain dense model at penguin goes to the engine only on a GPU of `GPUS` in `src/machine.rs` (the speed bar: the GPUs where the engine is measured at least as fast as vLLM at every load it would serve there, with less memory; today one line, the RTX 4080 SUPER, of 2026-11-20), unless `GLYD_ENGINE=1` asks for the engine by name or vLLM is not installed; every other family and level is the engine's whatever the list. `glyd serve` of a lossless model other than Gemma 4 is vLLM's unless `GLYD_ENGINE=1`; a level, a Gemma 4 model, a glyd-v7 directory and a `glyd/` repo vLLM cannot read go to the engine. The GPU is the one with the most free memory of those the driver shows (`CUDA_VISIBLE_DEVICES` names the ones to choose from); a family whose layers are cut over several GPUs (`Support::split_levels`) uses the others too, and Qwen3.8-Flash-Next runs on that one GPU: `--split` and a `--devices` of more than one are refused in words.

`preflight` looks at the model's config.json, the GPU a run would use and its driver (CUDA 13.0, driver 580 or newer, for a build with CUDA 13's kernels alone; a release also carries CUDA 12's and runs on 12.2, driver 535, and on 12.8, driver 570, for Blackwell), the computer's architecture (`ARCHS`: x86_64 and aarch64), whether the engine is used on that GPU (the speed bar), the memory the model takes there at the context asked for, and the disks (a first run writes the download and a packed copy). Every refusal that another runner can take is exit status 3, from `preflight` and from `run` and `serve` until they are up. `--status-file PATH`, which the program that starts `run` and `serve` gives, is how they say where they are: its modification time moves while they start, `ready` is written when they are up, and a refusal before that leaves its reason there as one line. Until `ready` nothing irreversible is done: standard input is read after it (a standard input known to be empty is refused at once) and no port is held. The `glyd` program runs the model with vLLM, in the same command, when the start ends in any way before `ready` (a refusal, an exit, a crash, a kill) or shows no sign of life for 15 minutes; after `ready` the engine's exit status is the command's.

**The plan and the degrade ladder** (`src/plan.rs`; `fit` prints it, `run` and `serve` follow it before anything loads). Where a model does not load at the level and context asked, the steps are: a shorter context, the experts or the dense layers of a large model kept in the computer's memory, a lower level. A shorter context and an experts-or-dense-layers step that costs at most 30% of the speed are taken and said; a lower level, or a step over 30%, is taken only with `--yes` (or `GLYD_DEGRADE=yes`), asked at a terminal by `run`, and refused by `serve`, the service and a run with no terminal (exit 3). The planner sizes every family with the functions the loaders use; `GLYD_KV=lossless` asks for the 12-bit KV pages, for Gemma 4 with `--no-draft` and, under `serve`, for the plain dense kind; the plan makes both formats' plans and takes the 12-bit pages only where they reserve no more than bf16 for it (both are lossless, so it never plans a lower level for them), else bf16. `fit` and `run` print which ("keys and values in bf16" / "in 12-bit pages"), the plan's JSON has `kv_format`, and the loader follows the plan.

**GEMM and sampling.** Long prompts multiply with cuBLAS where the machine has it, except on Ada (compute capability 8.9), where Glyd's own products take them; where cuBLAS is not there Glyd's own take Ampere and Hopper, and other GPUs keep the fused kernels (`dense_choice` in `src/gpu_ops.rs`; `GLYD_ENGINE_GEMM=own|blas` of a development build takes one). A step's draws are made from what the GPU leaves with the step (`src/sampler.rs`, `src/kern/mod.rs` `TopGpu`): the row's 64 largest logits, its sum of exponentials for a top-p with no top-k, its log-sum-exp for log-probabilities, a grammar's mask put on the row before its top-k, the changed tokens' own logits for penalties, a bias and a held-back end token (with a top-k of 1 to 64, or greedy), and, for a draw over the whole vocabulary, the row's weights in 1,024 buckets and the tokens of the bucket it lands in; the row is read to the host only where a draw comes within 1e-10 of a token's edge. `GLYD_ENGINE_HOST_SAMPLING=1` of a development build reads every row to the host, to compare the two.

**Variables.** A release build (`cargo build --release --no-default-features`; `GLYD_ENGINE_RELEASE=1` is release-gpu.yml's engine job: machine code for sm_80, 86, 89, 90a, 100 and 120, stripped) reads the API key (`GLYD_API_KEY`, `VLLM_API_KEY`), `GLYD_CACHE`, `GLYD_GPU_LIB`, `GLYD_KV`, `GLYD_DEGRADE`, `GLYD_MODELS`, `GLYD_NO_REFRESH`, `GLYD_SERVICE*`, `HF_*`, and these of the scheduler: `GLYD_ENGINE_BATCH_PREFILL` (by default the prompts that arrive together run in one pass, and a step of more than 16 rows gives a row another kernel than its own pass's, so a reply under load can differ from the same request alone in its last bits: `roundcheck` measures it; `=0` runs prompts one a pass, a round as two passes and the rows that decode in passes of at most 16, and every reply is the reply alone, bit for bit), `GLYD_ENGINE_ONE_STEP=0` (a round as two passes: a prompt's and then a decode step), `GLYD_ENGINE_KEEP=0` (a finished request's slot is emptied at once), `GLYD_ENGINE_OVERLAP=1` (a step is launched before the step before it is read; off by default), `GLYD_ENGINE_KV_EVENTS=1` and `GLYD_ENGINE_CACHED_USAGE=1` (`docs/serve-api.md`). The tuning variables are a development build's (the default features: the `dev` feature): `tune!("NAME")` is how the sources read one, and a release build neither reads nor names it. Every build keeps the kernels' own names.

**Development commands.** A development build has the checks, proofs and measurements of `src/devcmd.rs` (every command with its arguments is listed at its top): `pack MODEL OUT`, `generate`, `check`, `microbench`, `kcheck`, `kindcheck` (each layer kind's kernels against the CPU reference), `logitscheck` (`glyd-engine/docs/logits-tests.md`), `usercheck`, `roundcheck`, `keepcheck`, `kv12check`, `foldcheck`, `splitcheck`, `tpcheck`, `moecheck`, `hbcheck`, `tiercheck`, `packcheck`, `plancheck`, `bandwidth` and the rest.

## The API

The request fields, the replies, the refusals, the key, the Host and Origin checks, the limits and the operator's endpoints are in `docs/serve-api.md` (the contract, `glyd-serve/1`). The code is `src/server.rs` (requests, the key, the answers) and `src/server/` (`frontend.rs`: the connections; `anthropic.rs`, `responses.rs`, `ollama.rs`), with `src/choice.rs` (one choice of a reply: text, stops, thinking, tool calls, log-probabilities), `src/tools.rs`, `src/reader.rs`, `src/xtml.rs` and `src/families.rs` (each family's tool calls and reasoning as its template writes them), `src/wire.rs`, `src/conn.rs` (what a request's answer is written to), `src/engine_api.rs` (the request-level interface that no handler calls yet), `src/conv.rs`, `src/chat.rs`, `src/sampler.rs`, `src/constrain.rs` (grammars by llguidance), `src/tok.rs` and `data/chat.html`.
