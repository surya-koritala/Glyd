# glyd-engine reference

Glyd's own inference engine, in Rust: dense models of the Qwen3ForCausalLM architecture (none of the 2026 releases yet: Qwen3.5, Qwen3.8 and Gemma 4 run on vLLM) on an NVIDIA GPU (Ampere or newer) from Glyd-packed weights, every matrix compressed in GPU memory (the embedding and the LM head too), the lossless KV cache,
CUDA-graph decode, a chat in the terminal and at a URL, an OpenAI-compatible API for a few users at once. One program and Glyd's GPU library: the engine opens the CUDA driver and the library at run time, so the machine needs the driver and
nothing else (cuBLAS is used for long prompts where the machine has it). It ships in the glyd-gpu wheels (Linux, x86_64 and aarch64) beside the library, and `glyd run` starts it for
the models it runs on the GPUs where it is measured at least as fast as vLLM and with less memory (below: the speed bar); `glyd serve` is vLLM's, as the engine serves up to 8 users at once, unless `GLYD_ENGINE=1` asks for it. It has no measured results on a 2026 model yet, as it runs none.

    glyd run Qwen/Qwen3.5-9B                   # the glyd program (the Python tool, which the Rust one passes it to) asks glyd-engine first (`glyd-engine preflight MODEL`) and runs it as its child where it says it will certainly run the model here, else vLLM; one line says which (for Qwen3.5-9B: vLLM, as the engine does not run it)
    glyd-engine run MODEL                      # the first run downloads the model, packs it for this GPU and makes its KV tables; then a chat here and at http://127.0.0.1:8000
    glyd-engine run MODEL --prompt "Say hello" --no-think                # one answer on stdout (the thinking on stderr); a prompt on stdin works too
    glyd-engine serve MODEL --port 8000 [--api-key KEY]                  # the OpenAI API (/v1/chat/completions, /v1/completions, /v1/models), the chat page at /, the scheduler's counts at /stats
    glyd-engine doctor                         # the GPU, the library, cuBLAS, the caches' disks, the Hub
    glyd-engine login                          # a Hugging Face token (for gated models), saved where `hf login` keeps it
    glyd-engine supports MODEL                 # exit 0 if the engine runs MODEL's kind of model, 3 if not (no GPU is looked at)
    glyd-engine preflight [MODEL]              # before anything is downloaded: exit 0 if the engine will certainly run MODEL on this computer, 3 (the reason on stderr) if not, 1 if that could not be told; with no MODEL, the GPU alone
    glyd-engine --version
    glyd-engine fetch MODEL | prepare MODEL    # the model downloaded (no GPU) | downloaded and packed, the KV tables left for the first run

`preflight` looks at the model's config.json, the GPU a run would use (the one with the most free memory of those the driver shows: `CUDA_VISIBLE_DEVICES` names the ones to choose from) and its driver (CUDA 13: 580 or newer), the GPU's architecture (the engine has run on x86_64, on an A100, an L4, an RTX 4090 and an H100), whether the engine is used on that GPU (THE SPEED BAR: the list is `GPUS` in `src/machine.rs`, the GPUs where the engine is measured at least as fast as vLLM at every load it would serve there, with less memory, on a computer of `ARCHS`; the measurements decide it and it is EMPTY until they are made, so every model runs on vLLM; `run` and `serve` apply none of it), the memory the model takes there at the context asked for, the disks (a first run writes the download and a packed copy), and what the cache's tables said of the model before. Every refusal that another runner can take is exit status 3, from `preflight` and from `run` and `serve` until they are up. `--status-file PATH`, which the program that starts `run` and `serve` gives, is how they say where they are: its modification time moves while they start (every line or status they show), `ready` is written when they are up (serving, or about to answer), and a refusal before that leaves its reason there as one line, whatever its status, in place of the terminal. Until `ready` nothing irreversible is done: standard input is read after it (a standard input known to be empty, a file of no bytes or /dev/null, is refused at once) and no port is held. The `glyd` program runs the model with vLLM, in the same command, when the start ends in any way before `ready` (a refusal, an exit, a crash, a kill) or shows no sign of life for 15 minutes; after `ready` the engine's exit status is the command's.
`MODEL` is a Hub name (ORG/NAME), a directory in the Hugging Face cache layout, or a directory `pack` made. `--context N` (default 8,192, less where the GPU has less room; the model's own limit at most),
`--users N` (1 to 8, default 4: the replies decoded together; the cache's room for them is what the GPU's memory has), `--layout auto|mma|mma12`, `--temp T`, `--host`, `--port`, `-p` for `--prompt`.
`glyd run` and `glyd serve` give the engine the flags they were given and no others: the context is the engine's own choice from the GPU's memory (8,192 tokens, less where there is less room), and 4 users, unless asked for. Models and their packs are kept in the Hub cache (`HF_HOME`, `HF_HUB_CACHE`) and in `$GLYD_CACHE` (default `~/.cache/glyd`).
`GLYD_GPU_LIB` names the library (`libglyd_gpu_cuda13.so`, of C API 16: its functions are found by its table), else it is looked for beside the program and on the loader's path. A packed directory is glyd-v4: each matrix in the smaller of Glyd's two layouts (the tiered one, or the 12-bit one where it takes fewer bytes), the embedding's too; the engine loads each pack in its own. A directory packed in the tiered layout of glyd 0.27 and before (glyd-v1, glyd-v2), which the library no longer reads, is packed again, once, on its first use from the engine's cache (its KV tables kept), and refused in words where it is a directory the user keeps (`glyd pack MODEL DIR` again). `GLYD_ENGINE_GEMM=own|blas|lib` chooses how long prompts multiply
(the engine's own kernels, cuBLAS, the library's routes); unset: cuBLAS where it is, else the engine's own on Ampere and Ada. Sampling takes the 64 largest logits of every row of a step on the GPU and draws from those (as many as `top_k` asks for, to 64;
a request that asks for more, or for penalties, a logit bias, allowed tokens, a least length or log-probabilities has its row's logits read to the host: a bias can make a token that is not among the 64 the choice, and a
log-probability is the log-softmax of the whole row); `GLYD_ENGINE_HOST_SAMPLING=1` reads every row to the host, as the draws are compared. The lossy levels' engines (Qwen3.5 and Nemotron 3 Super, one user at a time) draw the same way from their one row: the 64 largest logits, and for a top-p with no top-k
(Nemotron 3 Super's own sampling) the sum of the row's exponentials too, are made behind the step and copied with its token; a top-p that the 64 do not reach, or come too near to tell, has the row read.

The release build (`cargo build --release --no-default-features`, `GLYD_ENGINE_RELEASE=1`: release-gpu.yml's engine job; machine code for sm_80, 86, 89, 90a, 100 and 120, stripped) has the commands above and `GLYD_CACHE`, `GLYD_GPU_LIB` and `GLYD_API_KEY`
as the variables it reads, and `GLYD_ENGINE_BATCH_PREFILL=0` (the prompts of up to 8 requests that arrive together run in one pass by default, so a reply's last bits can differ from the same prompt's alone; `=0` runs one prompt a pass and keeps every reply identical to solo; a deterministic mode is planned in #206). The commands below, and every `GLYD_ENGINE_*` variable of this file, are a development build's (the default features: the `dev` feature), left out of the release build to keep it small;
`tune!("NAME")` is how the sources read a variable of a development build. Every build keeps the kernels' own names (release builds up to v0.32.1 renamed them and were gated for leaks; the source is open now).

The development commands: `pack MODEL OUT`, `generate DIR PROMPT`, `check`/`score` (greedy tokens and teacher-forced scores for a vLLM reference, `tools/ref_vllm.py`), `bench`, `info`, `kvcal MODEL OUT`
(the KV tables, made on the engine's own forward pass), `rowcheck` (a sequence's logits with 0 to 7 others in the step; `--churn N` first reuses the cache for N rounds), `calcheck`, `kcheck`, `topkcheck` (the sampling kernels' candidates and sum of exponentials), `sampletime DIR PROMPT` (a Qwen3.5 or Nemotron-H model's decode speed by greedy steps, by sampled steps from the GPU's candidates and from the row on the host), `moecheck` (the mixture-of-experts layer on Int5, Int6 and Int4 experts against the CPU reference and PyTorch, and its speed at the four models' shapes), `hbcheck` (the Hummingbird layer's kernels against float64 and their speed), `hbtoy MODEL OUT` (a tiny Nemotron-H model packed at the Hummingbird level from a random export),
`bandwidth`, and the checks of the lossless cache: `kvtest` (host-made bf16 values of every kind written through the engine's write path and read back bit for bit), `stress` (requests of natural text or random tokens at several
users on a small cache, against the same requests alone, with every write compared with a bf16 copy at the step that makes it: `GLYD_ENGINE_VERIFY=1`), `recompute` (a sequence made by steps against the same one run again as a prompt).
`GLYD_ENGINE_RESERVE_1`, `GLYD_ENGINE_RESERVE_2` (percent of the cache) and `GLYD_ENGINE_RESERVE_1_UNITS`, `GLYD_ENGINE_RESERVE_2_UNITS` (sizes) set the cache's extra memory, as the plugin's `GLYD_KV_RESERVE_*` do: a size too small for a text is how
the engine's handling of a cache that cannot hold a value exactly is tried (the sequence's step is taken back and it runs again after the others, or it ends with an error in words).

The API (`/v1/chat/completions` and `/v1/completions`, streamed or whole): `tools` and `tool_choice` (auto, none, a named function, required; the model's `<tool_call>` blocks as `tool_calls`; a forced call begins in the prompt, the
thinking closed, and the arguments are the model's: no schema is enforced), `parallel_tool_calls`; `logprobs`/`top_logprobs` (up to 20) and a completion's `logprobs`; `n` up to 8 (the first choice runs the prompt, the others find its blocks
in the cache, seed + index each); `logit_bias`; `stop_token_ids`, `min_tokens`, `include_stop_str_in_output`, `allowed_token_ids`, `skip_special_tokens`, `reasoning_effort`, `documents`, `chat_template_kwargs`, `add_generation_prompt`,
`add_special_tokens`, `request_id`, `echo` (a completion's), a completion's `prompt` as ids or lists; the ranges and messages are vLLM's. Refused with a 400 that says so (and `GLYD_ENGINE=0`): `response_format` other than text, `guided_*`, `structured_outputs`,
`bad_words`, `prompt_logprobs`, `logprob_token_ids`, `thinking_token_budget`, `continue_final_message`, a chat's `echo`, `suffix`, `best_of` above `n`, beam search, and the other fields of vLLM's that are not done (`NOT_DONE` in `src/server.rs`). Not
done, and not refused: `model` (any name is the one model), `user` and the like (no effect here); a field the server does not know is said once on its standard error. Log-probabilities are the model's own (the log-softmax of the row before the bias, the
penalties, the temperature and top-k/top-p: vLLM's default `raw_logprobs`), the end token's among them, and the end token counts in `completion_tokens`, as vLLM counts it. On the address the program chooses (no `--host`: this computer's own) the server answers a Host of
localhost, 127.0.0.1 or [::1] only (421) and an Origin of its own page only (403, a preflight too), as the Python server's page guard did; with `--host` the checks are off and every origin is answered. The key (`GLYD_API_KEY`, `VLLM_API_KEY`, or `--api-key`, which `glyd run`
and `glyd serve` move to the environment before they start the engine) guards `/v1`, by SHA-256 digests; `--hf-token` is read the same way as `HF_TOKEN`.

A layer's experts are two groups by bits (hb40: 205 of 512 at three), each a layer of the cache with places of its width's size. `cpu_hb.rs` is the CPU half's kernels over the same bytes (scalar, NEON, AVX2, AVX-512, one set of bits; `HbPlace::expert` reads a place of the host tier in place, so the host's half takes no memory besides the experts': `ExpertStore::run_groups` (src/offload.rs) serves a layer of two groups with one wait, plans both groups' misses together, has the host compute the pairs it keeps from z' read back as fp32, and `hb_sum_rot` adds their sums before R^T and the one rounding); `hbcheck` (the kernels on a GPU against float64, and their speed), `hbtoy` (a tiny model packed from a random export) and `nhoffload` (which takes such a directory) are the development commands; the host emulator test runs the kernels without a GPU; where the computer's memory cannot hold them all (`--host-memory`) `HbDisk` reads an expert's six tensors, one run of the shard, into a slot of the host tier (`index_layer` finds each expert's width from glyd.json alone, so a layer loads without reading its experts); the pod job `../tools/cards/nh_offload_job.sh` with HB=1 |
